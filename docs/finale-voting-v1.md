# Голосование за финальные песни — v1 (закрыто по умолчанию)

## Состояние
Код разработан в отдельной ветке. Миграция `singer_finale_voting_v1` применена в Supabase и `singer-vote` Edge Function развёрнута 22.11.2026. Публичная страница будет доступна после слияния PR и деплоя. Открытие голосования безопасно ограничено активными временными окнами.

## Механика
- Публичная страница /vote/; вне времени активной сессии сообщает «Голосование пока закрыто».
- Ссылка «Голосовать за финальные песни» на главной **скрыта**, пока сервер не подтвердил активное голосование.
- В Supabase хранится отдельная сессия на каждый вечер; поле enabled по умолчанию false.
- Администратор открывает /vote/?manage=1, вводит секрет только в своём браузере, указывает начало и конец по московскому времени или закрывает вручную.
- Открытая/закрытая афиша не имеет значения. **Автоматическое открытие для публичных событий !В уже предусмотрено: сервер получает опубликованные временные окна kind=guest-mode, вычитает один час из установленного в том API двухчасового послесценического запаса и создаёт отдельную сессию только в промежутке начала–конца+1 ч. Для закрытых событий — ручное включение**: закрытые мероприятия в публичную афишу не попадают, их нельзя раскрывать ради голосования. Следующий этап — приватная публикация безопасных временных окон (без названий частных мероприятий) с явным согласием владельца.
- Гость выбирает ровно 3 разные песни; один набор на браузер в пределах одной сессии, повторный голос заменяет предыдущий. Результаты в панели управления обновляются каждые 5 секунд после успешной проверки секретного ключа.
- Сервер выбирает песни по символу @ в имени файла внутри playlist_variants существующего опубликованного каталога. Технические варианты объединены по song.id. Если @ при экспорте удаляется, нужно исправить экспорт, а не вести второй ручной список.
- Заказ другой песни из репертуара — отдельная ссылка, 1 000 ₽, оплата/исполнение только после согласования с артистом.
- IP используется только для ограничения частоты запросов, не для запрета другим гостям той же Wi-Fi сети. Сильной защиты от накруток без идентификации гостей нет.

## Развёртывание и проверка
1. Проверить, что опубликованный JSON содержит @ в filename у хотя бы 3 песен.
2. Выполнено: миграция применена к используемой сайтом базе Supabase (в том же проекте находятся и фитнес-таблицы, они не изменялись). Таблицы singer_vote_* имеют RLS.
3. Выполнено: в singer_vote_admin хранится SHA-256 администраторского пароля, исходный пароль не сохранён в коде. IP-rate-limit солится серверным секретом Supabase или отдельным SINGER_VOTE_IP_PEPPER; не публиковать исходные ключи.
4. Выполнено: Edge Function singer-vote с verify_jwt=false (публичный API проверяет admin Bearer; никакого service_role на клиенте).
5. Провести тесты: нет сессии, авторизация, 3 голоса, повторное голосование, ограничение частоты, закрытие и расписание; проверить владельца на отдельном устройстве.
6. После сборки PR и ревью опубликовать сайт. При отсутствии окна публикация /vote/ не делает голосование открытым.
7. Перед первым вечером протестировать вручную с пустой тестовой сессией. Выбирать победителей ведущему по рейтингу; их фиксация отдельными кнопками — следующий этап.

## Безопасность
Список открытых событий не источник разрешения на голосование. Включает только защищённое действие администратора; даже при ошибке чтения сервер возвращает закрытый или недоступный статус. SQL таблицы имеют RLS и закрытые прямые разрешения. Секретов в коде нет. Приватные детали мероприятия не публикуются.
